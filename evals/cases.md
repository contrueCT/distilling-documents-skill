# Evaluation Cases

这些 case 用于检查 skill 是否真的在做“可替代原文的精炼”，而不是普通摘要。

## Case 1：保留可重新推理的数据

源材料：

> 模型 MXFP4 权重约 1.4～1.5TB。8 张 H200 总显存约 1.13TB。因此在 8×H200 单节点上无法完整加载模型权重。

失败表现：

> 模型的硬件部署门槛较高。

通过标准：最终稿至少保留 1.4～1.5TB、8×H200≈1.13TB 和“因此装不下”的关系；可以合并成一句。

## Case 2：认识状态不能升级

源材料：

> 有分析估算，这次训练成本可能超过 2 亿美元；官方没有公布完整训练账单。

失败表现：

> 训练成本超过 2 亿美元。

通过标准：保留“估算/可能”和“官方未公布”的边界。

## Case 3：不能删除反向证据

源材料：

> 模型在多数通用 benchmark 上表现领先，但在长时 Agent 任务中仍明显落后于对比模型。

失败表现：

> 模型在多个 benchmark 上表现领先。

通过标准：精炼稿同时保留优势和 Agent 场景短板，整体判断不能被改写得更乐观。

## Case 4：技术文档不应被口语化破坏

源材料包含：问题、根因、方案、兼容性边界、配置项。

失败表现：改成聊天式长文，删除标题和条件，只留下“简单来说”。

通过标准：结构仍适合工程人员查阅；中文自然直接，但保持正式度、术语和精确条件。

## Case 5：默认零交互

用户只说：“把这份长文精炼一下。”

失败表现：先追问阅读目的、目标长度、读者、压缩比例。

通过标准：直接按通用替代稿处理；只有源材料缺失或确有不可消除的关键歧义才追问。

## Case 6：不输出中间过程

失败表现：向用户展示信息账本、KEEP/MERGE/DROP 表、删除理由、Probe 问答。

通过标准：默认只交最终精炼稿；上述机制仅在内部使用或用户明确要求审计时展示。

## Case 7：运行时不能依赖外部 human-writing

失败表现：`distilling-documents` 要求用户另外安装 `human-writing`，否则只使用明显更弱的降级规则。

通过标准：包内自带针对文档精炼适配的自然中文规则；没有外部 Skill 也能执行完整流程。

## Case 8：说人话不等于聊天口吻

源材料：正式技术设计文档，包含根因、兼容性边界和迁移方案。

失败表现：改成“简单来说”“说白了”“其实就是”一类聊天式解释，或者加入网络化语气。

通过标准：保持正式书面语和工程结构，同时减少长定语、抽象套话、模糊指代和翻译腔。

## Case 9：自然改写不能创造材料

源材料只说：“第三方价格一致，作者推测可能与许可证限制有关。”

失败表现：为了让文章更完整，补写第三方厂商与 Anthropic/Kimi 的谈判过程或具体商业动机。

通过标准：只重写现有信息；保留“作者推测/可能”的认识状态，不创造事实、动机或因果。

## Case 10：技术结构允许必要标点

源材料包含：`原因：`、`影响：`、`方案：`、配置项和代码块。

失败表现：机械执行散文式“禁冒号/禁破折号”，把可扫读结构改成连续长段。

通过标准：技术文类优先；标题、冒号、列表、表格、代码符号承担检索或执行功能时保留。
